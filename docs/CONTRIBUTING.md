# Contributing

Thank you for your interest in contributing to MCF.

MCF is built around simplicity, consistency and long-term maintainability.

Every contribution should strengthen these principles while remaining compatible with the overall architecture of the framework.

---

# Before Contributing

Before opening a Pull Request, please ensure you have:

- Read the project documentation.
- Understood the MCF architecture.
- Followed the coding standards.
- Followed the best practices.
- Tested your changes.

Contributions should integrate naturally with the existing framework.

---

# Philosophy

MCF follows a simple philosophy.

> **Every new feature should make the framework easier to use without making it more difficult to understand.**

Avoid introducing unnecessary complexity.

If a feature cannot be explained simply, reconsider its design.

---

# What Can Be Contributed

Contributions are welcome in many areas, including:

- Bug fixes
- Performance improvements
- Documentation
- CLI improvements
- New generators
- Developer experience
- Framework infrastructure
- Automated tests
- Code quality improvements

Well-documented contributions are always appreciated.

---

# Before Opening an Issue

Before reporting an issue:

- Verify the behavior on the latest version.
- Search existing issues.
- Ensure the problem is reproducible.
- Prepare clear reproduction steps.

A good issue report saves time for everyone involved.

---

# Reporting Bugs

A useful bug report should include:

- MCF version
- Laravel version
- PHP version
- Operating system
- Steps to reproduce
- Expected behavior
- Actual behavior
- Error messages or stack traces, if available

The more information provided, the easier the issue is to investigate.

---

# Feature Requests

Feature requests should explain:

- The problem being solved.
- Why the current behavior is insufficient.
- The proposed solution.
- Possible alternatives.
- Potential impact on existing projects.

Feature requests should focus on improving the framework rather than solving a single application-specific problem.

---

# Pull Requests

Every Pull Request should:

- Solve one problem.
- Be easy to review.
- Follow the existing architecture.
- Include clear commit history.
- Avoid unrelated changes.

Large Pull Requests should be divided into smaller logical changes whenever possible.

---

# Keep Changes Focused

Avoid combining multiple unrelated changes.

Good examples:

- Fix one bug.
- Improve one generator.
- Update one document.
- Add one feature.

Smaller changes are easier to review and less likely to introduce regressions.

---

# Follow the Existing Architecture

New code should follow the established MCF architecture.

Do not introduce alternative project structures or conflicting design patterns.

Consistency across the framework is more important than individual implementation preferences.

---

# Respect Existing Conventions

Contributions should follow the project's conventions, including:

- Directory structure
- Class naming
- Workflow organization
- Code formatting
- Documentation style

New code should look as though it has always been part of the project.

---

# Backward Compatibility

Whenever possible, avoid introducing breaking changes.

If a breaking change is necessary:

- Clearly document it.
- Explain why it is required.
- Describe any migration steps.

Maintaining compatibility helps existing projects upgrade with confidence.

---

# Documentation

Framework changes should include corresponding documentation updates.

Examples include:

- New CLI commands.
- New generators.
- Architectural changes.
- Configuration options.
- Behavior changes.

Documentation should evolve alongside the framework.

---

# Testing

Contributors are encouraged to test their changes before submitting them.

Verify that:

- Existing functionality continues to work.
- New functionality behaves as expected.
- No unnecessary regressions are introduced.

Reliable contributions improve the stability of the framework.

---

# Code Quality

Before submitting a Pull Request, ensure that the code is:

- Readable.
- Consistent.
- Well-structured.
- Properly organized.
- Free of unnecessary complexity.

Prefer simple solutions over clever ones.

---

# Commit Messages

Write clear and descriptive commit messages.

Good examples:

```text
Add CRUD workflow generator
```

```text
Improve endpoint generation
```

```text
Fix workflow discovery bug
```

Avoid vague messages such as:

```text
Update
```

```text
Fix
```

```text
Changes
```

A descriptive commit history makes the project easier to maintain.

---

# Documentation Style

When contributing documentation:

- Use clear language.
- Keep terminology consistent.
- Prefer short paragraphs.
- Organize content with headings.
- Include examples when helpful.

Documentation should be accessible to both new and experienced developers.

---

# Review Process

Every contribution is reviewed before being merged.

During review, maintainers may request:

- Code improvements.
- Documentation updates.
- Additional tests.
- Architectural adjustments.

Review feedback is intended to improve the quality and consistency of the framework.

---

# Community Guidelines

Please interact respectfully with other contributors.

Constructive discussions are encouraged.

Focus feedback on ideas, implementation and technical decisions rather than individuals.

A collaborative environment benefits the entire project.

---

# Summary

MCF welcomes contributions that improve the framework while preserving its core principles of simplicity, consistency and maintainability.

Whether fixing bugs, improving documentation, enhancing the CLI or extending the framework, contributors are encouraged to follow the existing architecture, keep changes focused, document new behavior and submit well-tested, high-quality work.
